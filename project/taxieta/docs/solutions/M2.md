## Key design decision: one definition, two execution modes
The stretch goal (“write the feature once”) is solved by keeping the *definition* in one place.
The window is `[pickup − 15 min, pickup)`, junk is filtered (`duration ≤ 60 s` or
`distance ≤ 0`), and events are ordered by event time, with starts before completions at the
same timestamp. Batch implements that with `searchsorted` over sorted completions
(`features.build.point_in_time_zone_speed`), and streaming with a per-zone deque. The test
proves they agree. Change the boundary (`<=` vs `<`), the filter, or the tie-breaking in only
one path and the match rate drops. That's exactly how train/serve skew is born.

## What to expect on real data
- **Parquet vs CSV:** Parquet is several times smaller. Reading 3 columns from Parquet is much
  faster than from CSV, because CSV must parse whole rows to pull 3 fields.
- **Iteration:** `iterrows` is orders of magnitude slower than column operations. NumPy row
  iteration is fast because the array is row-major (C order).
- **passenger_count:** on real data the missing/zero rate is *not* flat. Compare vendors and
  months. Differences mean MAR, so deleting rows would bias toward the vendors that fill it in.
  (On the fixture it's random, i.e., MCAR by construction.)
- **Rejection report:** expect a small percentage of rows rejected, mostly
  out-of-month timestamps, unknown zones (264/265) and negative or zero durations. Keep the report per month: a jump is an upstream incident.

## Learning-log answers
1. **Formats:** training data → **Parquet**. You read many rows but only the feature columns,
   and it's compact, typed and splittable. Appending events one by one → a **row-oriented log**
   (Kafka topic, JSON lines, a row store). Row-major formats make writes cheap (Ch. 3). A common
   pattern is to land events row-wise, then compact them into Parquet partitions on a schedule.
2. **Dataflow modes for zone speeds → prediction service:**
   - *Through a database:* the consumer writes to a DB and the API reads it. Simple, and fine
     at our scale, but DB round trips add latency and couple both services to one store.
     (That's what `stream/store.py` does with SQLite, and what Feast's online store does in M9.)
   - *Through a service (request-driven):* the API calls a “zone-speed service” per prediction.
     Adds a synchronous dependency: if it's down or slow, predictions are too.
   - *Through a real-time transport:* the API subscribes to a `zone_speed` topic and keeps the latest
     values in memory. Lowest read latency and decoupled, but every API replica must consume and
     keep state. For a data-heavy, many-consumer signal the book favors event-driven.
     A good production answer: the consumer writes to a low-latency online store (Redis / Feast)
     fed from the stream.
3. **Batch (static):** zone-pair × hour-of-week historical median, zone borough, airport
   flags, and anything computed from the lake. **Streaming (dynamic):** zone median speed over the
   last 15 minutes, and later counts of trips started in the last N minutes.
4. **Labels arrive later** because the duration is only known at dropoff (minutes to hours
   after pickup). So training data for time T is only complete after T + max trip length. Long
   trips arrive last (a window that closes early biases labels toward short trips). Features must
   be logged *at prediction time* and joined to labels later by `trip_id`. Recomputing features
   after the fact would use information that wasn't available at pickup.
